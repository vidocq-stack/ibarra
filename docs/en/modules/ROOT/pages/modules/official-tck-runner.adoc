= Official TCK runner
:description: Build-side Arquillian WAR adapter for Jakarta Pages 4.0 on modular Foy.

`ibarra-tck` is unpublished and enters the reactor only under `-Ptck`.
`-Ptck,tck-official` additionally resolves the official Pages 4.0.0 suite.
See xref:tck.adoc[TCK status] for the measured baseline and certification limits.

[source,bash]
----
./run-official-tck-pages-4.0.sh smoke
./run-official-tck-pages-4.0.sh all
./run-official-tck-pages-4.0.sh -Dtest=ee.jakarta.tck.pages.api.jakarta_servlet.jsp.jspwriter.URLClientIT
----

The script verifies distribution checksums, preserves the upstream Maven POM,
installs the non-Central artifacts, clean-installs Ibarra, tests the adapter,
and runs the requested official tests. Java 25, Maven 3.9.16 and Python 3 are
required. Local ZIP overrides and skip switches are documented in
link:{repo-ibarra}/src/branch/main/ibarra-tck/README.md[the runner README].

== Test tooling dependencies

The runner uses Arquillian container SPI, ShrinkWrap, JUnit and the official
`jakarta.tck:jakarta-pages-tck:4.0.0` jar with its original dependencies,
including `jakarta.tck:common`, `runtime`, `libutil`, signature tooling,
Apache HttpClient and `javatest:javatest:5.0`. This last tool is extracted from
an earlier Eclipse distribution because the Pages 4.0 ZIP omits it.
Only that tool is used from the older distribution; all tests are Pages 4.0.
These dependencies are test-only and never enter application artifacts.

The official profile also uses `maven-dependency-plugin` 3.8.1 to stage the
configured Pages/Servlet/EL API jars for the unchanged API signature driver.
`sigTestClasspath` contains only those API jars and the driver's extracted
`java.base` image (`jimage.dir`). Signature expectations are not rewritten;
this build-side classpath does not change application/host module isolation.
The ordinary adapter profile does not copy these signature resources.

== Runtime isolation

The build-side adapter precompiles each WAR as a named application module,
then launches Foy/Chappe in a separate process on the module path.
The server rejects the presence of `java.compiler` or either compiler module;
Peano reflection remains denied. Application packages have no added exports
or opens. Multiple WARs have independent ports, lifecycles and resource roots.
Retained server logs and Surefire reports are in `ibarra-tck/target`.

Root web.xml property groups are parsed at build time, with matched scalar settings,
ordered preludes/codas and legacy EL defaults. The runner explicitly selects
`PagePrecompiler.precompileDeployment`: valid pages compile normally, while genuine
parse/generation/javac failures produce direct error servlets that throw on request.
The full diagnostic is retained in `translation-errors.txt`; error messages are
bounded without splitting Unicode characters. Previous generated classes cannot
satisfy new incremental dependencies. Normal packaging remains fail-fast.

[source,java]
----
var groups = new JspConfigurationParser().parse(
        "/WEB-INF/web.xml", Files.readAllBytes(webRoot.resolve("WEB-INF/web.xml")));
var report = new PagePrecompiler().precompileDeployment(
        webRoot, classes, modulePath, null, new GenerationOptions(groups, Map.of()));
// report.pages() includes routable valid/error pages; report.failures() is immutable.
----

These APIs belong to the build-only `io.vidocq.ibarra.compiler` package.
Global property keys, booleans, encoding and buffer capacity are validated before
individual page recovery, even for an application with no pages. Invalid global
settings leave previous generated output ownership intact.

== Descriptor component factories

Root web.xml servlets, filters and listeners whose bytecode is in WEB-INF/classes
receive build-generated Foy `WebComponent` providers. The Class-File API emits
direct class literals and no-arg constructor calls, without initializing component
classes during discovery. The named application module explicitly requires
`io.vidocq.foy.api` and declares the providers through `provides`; packages retain
no exports or opens. Existing page provider registrations are preserved.

Components must be public concrete classes with public no-arg constructors.
Missing classes, invalid constructors and generated provider name collisions
abort deployment before server launch.
Generated factories preserve runtime exceptions/errors and wrap checked constructor
failures with their cause, including constructors declared to throw Throwable.
Foy continues to apply descriptor mappings, init parameters, startup order, filters
and listener lifecycle. This adaptation
belongs to the unpublished test runner; the production Maven plugin is unchanged.

== Legacy WAR libraries

The runner assembles ordinary WEB-INF/lib JAR bytecode and resources into the
existing private application module. Legacy WARs may share packages between
WEB-INF/classes and several libraries; assembly keeps that overlap inside one
explicit module, without automatic modules, exports or opens. Equal duplicate
outputs are deduplicated; incompatible class/resource collisions fail explicitly.

Original JAR bytes are retained for physical TLD references. Library META-INF TLDs
receive separate build-discovery paths, preserving URI discovery when several
libraries use META-INF/taglib.tld. Other resources retain their module-relative
paths. Parsing happens during the build; the server receives compiled pages only.

Unsafe/noncanonical ZIP paths, explicit module descriptors, multi-release entries,
web fragments and classpath service metadata are rejected before runtime because
their semantics still need separate adaptation. This is a bounded unpublished
test-runner feature; production Maven packaging remains unchanged.

The adapter explicitly rejects unadapted library metadata, Servlet annotation metadata and
initializers that it cannot yet adapt. Invalid global configuration and TLD
metadata still abort deployment. These remain visible full-suite errors.

== Private bean property tables

Legacy WAR bean properties receive build-generated Peano AccessorTable/AccessorProvider
services in the existing application module. Class-File metadata supplies direct
getter/setter calls, boxing and ELContext conversion. Inherited property lookup
honours boolean getter precedence, covariant returns and compatible most-specific
setter overloads. Null, read-only and write-only properties preserve resolution flags.

Tables stay in the bean package without exports/opens; neither metadata discovery
nor provider class literals initialize bean classes. Map, List, ResourceBundle and
Record hierarchies retain native resolver semantics. Runtime reflection stays denied.

Lookup follows actual module reads/exports, including qualified exports; exact
resource checks avoid unrelated package-owner masking. Unsupported hierarchy or
signature types are reported in bean-accessor-errors.txt without registering an
unusable target. Binary identity mismatches and class collisions fail adaptation.

This unpublished runner feature covers properties. General method invocation,
static members, conversions/functional adapters and explicit BeanELResolver calls
remain follow-up capabilities. Production compilation and dependency contracts
remain unchanged; no runtime parser, compiler or new SPI is introduced.

== Collection method tables

After pages compile, Class-File allocation metadata selects public concrete
java.util Collection types from java.base. Method-only tables stay in the private
application module; their provider is appended while preserving all compiled
PageIndex, Foy component and bean services. No WAR fixture is rewritten.

Peano's existing MethodDescriptor and MethodSelection provide direct metadata and
overload selection. Invocation converts through the supplied ELContext and retains
primitive/void/null results and exception causes. Metadata does not invoke methods;
argument arrays are copied. Exact runtime types are required. Unknown targets/names
and all property operations stay unresolved, preserving native list indexing.

Signature visibility is checked from the helper package using actual module
reads/exports. Names with varargs, runtime annotations or inaccessible signature
types are omitted with bean-accessor-errors.txt diagnostics. Inherited Object and
static methods remain outside this capability. Discovery does not initialize
application classes; generated-name collisions abort without overwriting originals.
This adaptation is confined to the unpublished runner; production applications
still provide their own complete Peano accessors.
