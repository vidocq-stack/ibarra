= Compiled EL
:description: Build-time Peano expressions in application-owned Java modules.

== Build and runtime contracts

`ibarra-compiler` uses the build-only dependency `io.vidocq.peano:peano-compiler`
at `peano.version`, plus its Peano core/API transitives. This dependency emits
EL class files through the Java 25 Class-File API and avoids duplicating Peano's
compiler or introducing runtime parsing. The Maven plugin receives it through
Ibarra compiler. Neither compiler module belongs in the runtime graph.

Applications whose pages use EL add `io.vidocq.peano:peano-api` and an explicit,
non-static module read:

[source,java]
----
module example.pages {
    requires io.vidocq.ibarra.api;
    requires io.vidocq.peano.api;
}
----

Core and Foy binding keep their existing dependencies. Runtime evaluation obtains
an ExpressionFactory through the standard Jakarta EL API; Peano core is the
default provider in Vidocq. Application packages require no exports or opens.

== Generation and packaging

Default generation compiles immediate expressions into classes beside their
page and directly constructs immutable static-final ValueExpression fields.
Evaluation receives the request's EL context; generated classes retain metadata
without request or creation-context capture. Invalid EL retains its page origin.

`GeneratedPage.auxiliaryClasses` carries immutable `GeneratedClass` values with
defensive byte arrays and content equality. PageCompiler validates binary names
and source/auxiliary collisions, writes bytecode before javac, and verifies javac
has not replaced those classes. Direct callers include source and bytecode roots
in their target module patch. PagePrecompiler configures that patch, publishes
from staging, and tracks expression classes in its ownership manifest and module
package metadata. Removing EL removes obsolete expression classes without
claiming application-owned files.

`withStartupEl(true)` remains an explicit interpreter preview. Production
packaging rejects it; compilation failures never select runtime parsing.

== Resolvers and private application types

The Pages chain retains the provider's standard `getStreamELResolver` hook after
application resolvers and before standard property resolvers. With Peano this
includes generated accessor tables and collections. Context creation uses the
page's defining loader to discover child-layer services, restoring the caller
loader on success or failure.

Applications generate/register private property and method tables through
https://codefloe.com/Vidocq/peano[Peano's processor] or its public AccessorProvider
contract. This permits direct access with `peano.reflection=deny`, without
exports/opens. Ibarra core introduces no Peano-specific runtime lookup.

The unpublished official runner now adapts legacy WAR property access through
Class-File-generated Peano services, because its original bytecode has no processor
output. It retains reflection denial and private packages. This bounded property
feature does not change production compilation or provide general method/static
member access; see xref:modules/official-tck-runner.adoc[the runner reference].

== Page imports

Page directives import explicit types, public nested types or packages. The four
implicit packages are java.lang, jakarta.servlet, jakarta.servlet.http and
jakarta.servlet.jsp. Includes contribute their imports to the translation unit;
fragments retain their originating page's metadata.

Class-File inspection enumerates visible public types without initializing them.
The precompiler supplies the application descriptor, filtering wildcard candidates
by module readability and qualified/unqualified exports. Direct PageGenerator
callers can supply that descriptor through its compatible overload. Public nested
types are resolved using binary-name metadata; wildcard imports include top-level
types only. Preview-only wildcard classes are excluded from non-preview builds.

Generated PageOptions methods resolve simple names with lazy direct class literals,
without runtime class-name loading. Explicit imports take precedence; ambiguous
wildcard names fail when requested. Scoped attributes precede ImportELResolver,
which precedes the not-found policy. Static fields/methods retain the provider
resolver before the standard static-field fallback, so Peano reflection denial
continues to apply. Handwritten pages retain standard ImportHandler defaults.

Precompiled pages explicitly reject runtime importClass/importPackage/importStatic
mutations instead of accepting changes their fixed table would ignore. Static
member syntax is not accepted by the page directive's type/package import grammar.
The handwritten fallback's abstract/interface restriction in Jakarta ImportHandler
is tracked separately in BUG.md; generated direct bindings are unaffected.

== TLD functions

Declare functions in a discovered TLD, alongside tags or in a function-only library:

[source,xml]
----
<function>
  <name>welcome</name>
  <function-class>example.Functions</function-class>
  <function-signature>java.lang.String welcome(java.lang.String)</function-signature>
</function>
----

A standard page binds the prefix with a taglib directive and calls
`${example:welcome(param.name)}`. JSPX uses the library URI as its plain namespace
or forces a descriptor path with `urn:jsptld:/tlds/example.tld`. A forced path
bypasses URI aliases; it does not accept another absolute URI after the prefix.
XML prefix bindings follow lexical scope, including named-attribute/text wrappers;
included relative declarations retain their own resource origin.

Peano's expression AST exposes every qualified call and argument count. Ibarra
looks up the TLD and inspects class files without initializing the owner. Invoked
methods must be public static with exactly the declared parameter and return
types. Fixed-arity overloads, inherited public static methods, primitives, arrays,
public nested types and void returns are supported. The owner needs no constructor
and may be abstract. Varargs methods, generic signatures, missing bindings and
wrong arities fail translation. Javac checks signature accessibility from the
application module before staged output is published.

Each binding supplies Peano's `CompiledFunctionMapper` with an immutable
`FunctionDescriptor` and a serializable generated `CompiledFunctionInvoker`.
The invoker calls the method directly, applying `ELContext.convertToType` to each
argument using the evaluation context. Void calls return null. Expression fields
retain signature metadata and stateless callbacks, never requests or creation
contexts. Runtime evaluation needs neither reflective Method lookup, accessor
registration, TLD XML nor class-name loading. Unprefixed calls keep their usual EL
resolution; these bindings apply to qualified TLD functions.

The catalogue discovers WEB-INF resources and library resources, plus explicit
web.xml aliases or supplied generation metadata. Direct declarations also load
TLD/JAR snapshots outside those roots, keeping resource bindings separate from
URI aliases and registering their listeners. Libraries with `TagLibraryValidator`
metadata receive the generated PageData XML during servlet initialization,
including function-only libraries. Request-time attribute expressions in that
XML view use the JSP XML syntax `%=`.
Interpreter preview does not support these descriptor-only bindings and fails
explicitly. Deferred attributes and runtime function-map mutation remain outside
this implementation.

== Deferred tag attributes

TLD attributes may declare `deferred-value` with an optional expected type
(default Object), or `deferred-method` with an optional method signature
(default `void method()`). Pure setters must accept ValueExpression or
MethodExpression exactly. Combining either declaration with rtexprvalue=true
requires an Object setter; the dynamic type and deferred expected type remain
separate contracts. Fragment/deferred conflicts and malformed signatures fail
descriptor parsing. Expected classes are inspected without initialization;
staged javac validates module accessibility.

Simple reference names in deferred expected types and method signatures resolve
in `java.lang`: for example, `Object`, `Integer` and `String[][]` have the same
meaning as their fully qualified forms. Array dimensions are preserved. Other
reference types must use qualified names; page imports do not qualify TLD types.
This translation support does not supply direct method metadata for arbitrary
receiver classes. Production applications register complete Peano accessor
providers for their method targets. The unpublished official TCK runner now
generates method-only tables for allocated java.base collections, allowing
deferred `Vector.add` with Peano reflection disabled (IBARRA-114).

[source,xml]
----
<attribute>
  <name>target</name>
  <deferred-value><type>java.lang.String</type></deferred-value>
</attribute>
<attribute>
  <name>action</name>
  <deferred-method>
    <method-signature>java.lang.String documented(java.lang.String)</method-signature>
  </deferred-method>
</attribute>
----

Use `target="#{param.name}"` and `action="#{profile.greet}"`. The signature's
method name is documentation only; its return/parameter classes define the
expected method contract. Peano compiles both expression forms at build time.
Generated code directly constructs an expression per tag invocation, capturing
the current VariableMapper bindings and immutable TLD function descriptors.
The temporary construction context is discarded; container request/page contexts
are not stored in expression fields. User-supplied mapped expressions retain
their own normal binding/lifetime semantics.

Pure deferred values accept literals and hash expressions; literals remain
isLiteralText=true and values are coerced when the handler evaluates them.
Methods accept hash expressions and convertible non-void literals. Literal method
validation supports primitive/boxed scalars, String/Object and BigInteger/BigDecimal;
other literal return targets fail explicitly at translation. Nonliteral signatures
may use public application types and arrays. Mixed attributes defer only active
hash syntax; literals, dollar syntax and scripting values are evaluated immediately
using the dynamic contract. Escaping, EL-ignored and deferred-literal policies
are applied before classification. A single attribute cannot mix active dollar
and hash expressions.

Named deferred attributes accept trimmed text and EL, with scoped bindings on
named/text wrappers. Executable named-body capture and composites rebinding one
function name to different targets remain explicit diagnostics. Preview mode
does not silently replace deferred compilation with parsing.

Literal protocol classes are emitted through the Class-File API rather than
reparsing escaped literal data. They preserve source/literal metadata, long strings
and serial identities. A generated method adapter keeps only a class anchor and
delegate. Metadata/reference lookup and invocation use the application's loader,
restoring the caller loader in finally, including failure and concurrent calls.
This exposes the application's generated accessor tables with reflection denied
even when the caller thread belongs to the host layer. No ClassLoader or
PageContext is serialized by the adapter.

== Remaining work and proof

Immediate template/action/tag EL uses the delivered compiler, including scopes,
map/list navigation, operators, calls, lambdas and fixed-arity TLD functions.
Typed deferred tag attributes are implemented within the boundaries above.
Immediate static expressions use class-only constructors; deferred tag expressions
capture the invoking context's VariableMapper through per-invocation constructors.
I3 remains in progress; the initial official Pages TCK baseline is available in
xref:tck.adoc[TCK status], with full certification pending.

A packaged named-module fixture renders with both compilers excluded and a
factory that rejects every runtime expression-creation call. HTTP JSP/JSPX tests
render repeated request values, TLD functions and private beans with Peano reflection denied.
Tests cover bytecode immutability, collisions, diagnostics, required module reads
and incremental cleanup. The independent Maven example compiles EL through the
actual precompile goal, calls a TLD function and explicitly requires Peano API.
The local Ibarra reactor passes 282 tests. Peano's compatible prerequisite passes
303 tests and 361/361 official EL TCK tests. The official Pages TCK now has an
initial diagnostic baseline; these unit and integration results are not Pages certification.
Deferred fixtures also verify setter overload selection, writability, variable
capture, literal interpreter agreement, serialization, loader restoration and
private-bean method dispatch over HTTP in both JSP syntaxes.
