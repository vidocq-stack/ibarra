:description: Ibarra's planned architecture — modules, translation pipeline, Foy SPI, Peano integration.

[.lead]
How Ibarra is designed to work inside. The runtime in `ibarra-core` implements milestone I1; the full design is `PLAN.md` in {repo-ibarra}[the repository].

== Output writers (implemented)

`BufferedJspWriter` acquires the response writer only when output must be sent.
It uses a character buffer (8192 characters by default), flushes on overflow
with `autoFlush=true`, and throws `IOException` on overflow otherwise.
`clear()` fails after flushing; `clearBuffer()` discards pending buffered
output. Closing flushes and closes the destination.

`BufferedBodyContent` captures tag output without flushing to its enclosing
writer. The body is unbounded, can be read or copied repeatedly, and can be
cleared between iterations. Nested bodies remain independent. Its inherited
`flush()` always throws `IOException`; closing never closes the enclosing writer.

Both classes are internal and request-owned. They introduce no module exports,
runtime dependencies, shared state or handler pooling.

== Page context and factory (implemented)

`IbarraPageContext` stores page attributes locally and delegates request, session
and application scopes to the Servlet API. Session access is opt-in. Nested
body pushes update the implicit `out` attribute; pops restore the previous writer.
Includes route through the current writer, preserving output order and body
capture. Forwards discard pending output and reject committed responses. Error
pages receive Servlet error attributes and the Pages exception attribute; after
commitment they are included. Release drops request state without pooling.
Page code flushes or closes output before releasing its context.

`IbarraJspFactory` allocates fresh request contexts and shared application contexts.
The future container binding installs it with `JspFactory.setDefaultFactory()`
and removes application contexts only after requests have drained.

== Application EL context (initial implementation)

Application resolver registrations freeze atomically on first context creation.
Provider lookup is lazy and happens once per application. Each page caches its
EL context before notifying listeners so callbacks can retrieve it safely. A
failed callback clears the cache for a later retry. Application and standard
collection/bean resolvers precede the scoped-attribute resolver.

The final not-found resolver reads the immutable page policy before listeners
run. Strict pages reject unresolved EL lookups; explicitly resolved nulls remain
valid. Two pages in the same application can use different policies.

Scope, parameter, header, cookie and initialization-parameter implicit objects
are implemented and exercised with Peano. Headers use case-insensitive lookup.
Page type/package imports and fixed-arity TLD function bindings are generated at
build time; runtime import mutations remain open. Some API tests also use a concrete
factory double to isolate lifecycle semantics.

== Translation pipeline (planned)

Parsing, initial Java generation and build-time javac exist. Full translation
semantics remain unfinished. Build-time Peano EL and page-index packaging are implemented.

. Parse the page (standard or XML syntax) into a page model, applying `jsp-config` property groups and TLDs.
. Generate the Java source of an `HttpJspPage`; page expressions are compiled by Peano's build-time compiler.
. Compile with `javax.tools` in the build JVM; emit a page index registered through `ServiceLoader`.

A Class-File API back end for scriptless pages (no `javac` at all) is a later option.

== Page parser (implemented)

`PageParser` consumes decoded source strings and produces immutable nodes for
template text, EL expressions, directives, scripting and nested elements. It
selects XML syntax for `.jspx`/`.tagx` and a document-level JSP root; callers can
explicitly select syntax and supply EL defaults through `ParserOptions`.
Page/tag EL directives apply to the whole document.

Standard syntax preserves ordinary markup and HTML comments while removing
JSP comments. XML syntax uses the JDK StAX parser, recognizes the JSP namespace
by URI, decodes XML character references and CDATA, and preserves whitespace
inside `jsp:text`. Node locations refer to the original source, including before
XML decoding, with one-based lines and UTF-16 columns. `PageParseException`
provides the location separately from its build-readable message.

Parsing requires `java.xml`; generation/compilation additionally needs the
optional `java.compiler` module. The module exports only its public API.
Initial attribute handling and static include expansion exist. `PageGenerator`
accepts decoded text or strictly decoded byte sources, including independently
encoded static resources. BOMs and XML byte signatures/prologs are detected
before parsing; encoding directives are scanned with the standard lexer rather
than matched inside comments or EL strings. Full semantic validation remains open.
DOCTYPE declarations and external
entities are unsupported in this initial parser; no external documents are read.

== Initial Java generator (I3 in progress)

`PageGenerator` emits a public page and a package-private lifecycle base. Final
Servlet entry points initialize expression fields before invoking user `jspInit`
and preserve `jspDestroy`. Generated request code obtains/releases a PageContext,
handles errors and flushes buffered output without flushing after a forward.

The current action set includes include/forward/param, useBean/getProperty/
setProperty (including wildcard parameter tables), text, dynamic elements and
named attribute/body capture. Bean construction and property calls are direct;
metadata comes from the Class-File API. Javac checks module accessibility.
Property actions resolve the current scoped attribute rather than a stale local.

`PageCompiler` is build-only. It writes Java 25 classes and retains generated
source under `.ibarra-sources`; compile errors map back to page locations.
Fixtures run generated classes on the module path with direct construction.
The core module is patched only for the unit fixture's internal factory access;
an additional I4 fixture packages a separate application JAR and discovers its
unexported pages through the Java module service declaration, with compiler
modules excluded. Initial I5 also verifies HTTP deployment on Foy/Chappe.

== Modular packaging (initial I4)

`PagePrecompiler` emits application pages and a `PageIndex` with direct constructor
references. The JDK Class-File API updates only the compiled module's service and
package metadata; existing providers, exports, opens and requirements are preserved.
The core's `PrecompiledPages` catalogue discovers indexes in a supplied module
layer without creating servlet instances. Deployment creates and initializes pages.

Compilation runs in a temporary staging area; generated Java does not enter the
application JAR. An external ownership manifest records generated class digests
so incremental removal cannot overwrite/delete classes replaced by application
compilation. Generation/compilation failures retain the previous output.

The xref:modules/maven-plugin.adoc[Maven goal] binds to `process-classes`, parses
root `web.xml` JSP property groups without external documents, and compiles using
the application module path. Maven's own plugin classpath is a build-only exception.

Default EL uses build-time Peano classes and directly constructed static-final
ValueExpressions, evaluated against each request's EL context. Provider resolver
hooks retain generated accessor dispatch in closed application modules. The old
interpreter path requires `withStartupEl(true)` explicitly and is unavailable in
production packaging. Page imports resolve lazily through generated class literals.
TLD functions use immutable Peano descriptors and generated direct static invokers.
Shared-scope bean lookup/construction/publication use an application-owned
reentrant lock; creator-only bodies run after unlocking.
Typed deferred tag attributes capture variables/functions per invocation and
scope method metadata lookup to the application loader with finally restoration.
Runtime import changes,
bean creation and full semantic validation remain open.
Mixed-syntax includes/preludes/codas structure each file before expanding the
translation unit, then apply the global EL policy. Source syntax remains available
for text escapes and XML markup generation. Each file's `pageEncoding` is validated
independently; only the requested page influences response encoding defaults.
New shared-scope beans use direct construction; existing
typed shared beans are supported. This is not TCK certification.

== Foy integration

Foy API exposes the optional `JspEngine` service. Deployment opens an application
with its `ServletContext` and Java module layer before initializers/listeners.
The binding supplies `*.jsp` / `*.jspx` routing and fresh named JSP instances.
Foy exposes immutable `JspConfigDescriptor` views and closes engine state after
component destruction. Without an engine, JSP remains unmapped. TLD listeners
use build-generated constructor factories and the normal container lifecycle;
see xref:modules/foy-binding.adoc[the binding reference].

== AOT compatibility

Target: no compiler and no class loading by name at run time in production, no reflection in generated code, no `opens`.
